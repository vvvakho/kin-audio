# 6 Oct 2026

## Intent

I decided to treat Kin as an open research project rather than attach another general music model to the plugin. The contract is content-preserving re-instrumentation: I author the notes, timing, dynamics, and phrasing; the model changes the performing body.

## Landed

`vvvakho/kin-audio` is public under Apache-2.0. It contains a deterministic paired-corpus generator, monophonic pitch and loudness extraction, a compact DDSP-style harmonic renderer, reproducible CPU/CUDA environments, training and inference commands, structural evaluation, tests, CI, and a dataset registry.

The first end-to-end smoke model trained from generated CC0 pairs and completed inference. On that controlled corpus it measured 2.1 cents median pitch error, 97.4% voicing overlap, and 75.5% of jointly voiced frames within 50 cents. These numbers validate the pipeline, not musical quality or real-recording generalization.

A read-only Gradio dashboard runs on the home PC and is reachable from my phone over the private Tailscale network. It shows project state, approved datasets, run metrics, and model-versus-target listening artifacts.

The main training path now also includes an audio-to-audio complex-spectrogram U-Net. A 53,450-parameter CPU smoke run trained for four epochs on 32 aligned synthetic examples containing both chords and single notes. The dashboard exposes input, trained-model output, and target reference together, and defaults to the newest run.

The first polyphonic checkpoint was effectively an identity transform: its source/output normalized
error was only 0.0000307 and correlation rounded to 1.0. Zero-initializing the residual projection
prevented useful gradients from reaching the encoder. The corrected model uses a trainable
projection from the first step and an absolute frequency-position channel for formant learning.
Its held-out dashboard example is a three-voice chord, and source/output normalized error is now
0.30 rather than effectively zero.

The private mobile dashboard now accepts a recording or upload of up to 15 seconds and runs it
through the selected polyphonic checkpoint. The interaction was exercised end to end with an
uploaded chord and returned a playable model render.

## Decisions

GitHub holds code, review, CI, and engineering history. Hugging Face will hold public datasets, model cards, weights, and eventually the demo. Cloud NVIDIA is the canonical full-training environment; the RX 7800 XT remains useful for preprocessing, inference, and short experiments, but Arch is not an officially supported ROCm host.

Public data must have explicit provenance and compatible redistribution terms. Ableton Packs can inform private experiments but will not enter released datasets or weights without written permission. StarNet is the first paired real-audio benchmark; NSynth and Slakh are supporting corpora. Splits are made by composition rather than random audio chunks.

The intended musical model is polyphonic from the beginning. Monophonic phrases stay in the same training distribution and use the same architecture; the explicit-pitch DDSP model remains an interpretable diagnostic lower bound. This avoids spending the real-data budget on an architecture that cannot represent the target use case.

Audio input is the useful prompting surface at this stage. Text conditioning is not part of the
baseline and should not be implied by the dashboard language.

## Current state

The public repository and CI are healthy. The active `polyphonic-smoke-v4` checkpoint has 53,522
parameters, trained for 40 CPU epochs, and reached 0.95606 validation loss on the synthetic corpus.
Both live model families are still smoke artifacts and are intentionally not published as model
releases. The dashboard output is generated from saved trained checkpoints, but the corpus is
deliberately controlled and does not establish musical quality. The next credible evidence must
come from a leakage-safe StarNet subset and real source recordings. Local storage is too small for
full StarNet or Slakh extraction, so real-data work needs streamed subsets, added storage, or cloud
object storage.
